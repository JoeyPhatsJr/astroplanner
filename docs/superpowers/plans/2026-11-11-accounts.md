# Accounts and Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Local accounts (create, sign in, sign out, change password, delete) so that session plans, AstroLog and the Processing Coach belong to one signed-in user each, while Tonight, Explore, Variable Hunter and the site pages stay open.

**Architecture:** A new `backend/app/accounts/` package holds the `users` and `user_sessions` tables, Argon2id hashing, cookie sessions, the throttle, the `current_user` / `optional_user` dependencies, the `/api/auth/*` routes, account deletion and the reset-password CLI (`python -m app.accounts`). A second migration adds `owner_id` to every plan, AstroLog and coach table and makes the dedup keys unique per owner. Every owned route filters by owner and answers 404 for someone else's row. On the frontend, one `/api/auth/me` query drives the header slot, the AstroLog gate and the session-plan prompts.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic, argon2-cffi, pytest; React 19, TypeScript, TanStack Query 5, react-router-dom 7, Vitest + Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-11-accounts-design.md` (binding). Mockup: `docs/superpowers/mockups/2026-11-11-login/index.html` (serve the repo root with `python3 -m http.server`, then open that path). Use it for screens and copy only; its CSS is a picture, so build with the app's own tokens and classes. Read both.

## Spec decisions made in this plan

- **Sign-up throttle** counts *failed* sign-ups only (409 existing email, 422 rejected email or password), per client address: 5 in 15 minutes locks that address for 15 minutes. Counting every sign-up would lock out the e2e suite, which creates many accounts from 127.0.0.1.
- **`/api/auth/me` also returns `claimed_existing: bool`.** The Account page needs it to show "Your existing plans and AstroLog library were added to this account." It is stored on `users.claimed_existing`.
- **Copy corrections, where the approved text would be inaccurate:**
  - Gate: "…with your account. Sign in to open it." The approved text said "so they’re there on any device", which a single-computer install cannot promise.
  - Privacy "What it keeps": "Your account: your email and a password hash". The spec's "encrypted password" contradicts its own "a password hash (never the password)".
  - Account "Your data" and the delete dialog now name session plans, since plans are owned.
  - The delete dialog adds a Password field, because `POST /api/auth/delete` requires one.
- **Two migrations:** `0006_accounts` (Task 1) and `0007_ownership` (Task 2). Each task then ends with its schema matching the ORM.
- `session_targets` gets no `owner_id`. It is reached only through its owned `sessions` row, and the database cascade removes it with that row.

    - Otherwise it runs `UPDATE <table> SET owner_id = :uid WHERE owner_id IS NULL` for each model and sets `user.claimed_existing = (any rows updated)`.
    - The flag is written even when nothing is updated, following the `canon_seeded` pattern.
  - Sign-up calls it in the same transaction as the user insert.
- `run_migrations` change (the data-loss guard). On SQLite, Alembic batch mode rebuilds a table by dropping and copying it. With `PRAGMA foreign_keys=ON` (set on every connection by `Database`), dropping `library_targets` or `stacks` fires the children’s `RESTRICT`, `SET NULL` and `CASCADE` actions. So for SQLite only:
  1. Open a connection.
  2. Run `PRAGMA foreign_keys=OFF` and commit, outside any transaction, because the PRAGMA is ignored inside one.
  3. Run the upgrade in `conn.begin()`.
  4. Run `PRAGMA foreign_key_check` before committing. If it returns rows, roll back and raise `RuntimeError("Migration would leave broken references; nothing was changed.")`.
  5. Restore `PRAGMA foreign_keys=ON` in `finally`. The in-memory `StaticPool` connection is shared.
  Postgres keeps today’s path.
- Dropping the unnamed column-level uniques in 0007 needs a different approach on each dialect:
  - **SQLite:** `op.batch_alter_table(t, naming_convention={"uq": "uq_%(table_name)s_%(column_0_name)s"})`, then `drop_constraint("uq_<table>_<column>", type_="unique")`.
  - **Postgres:** read the real name with `sa.inspect(bind).get_unique_constraints(t)`, which gives `<table>_<column>_key` by default.
  The docstring states that `downgrade()` fails if two owners hold the same key, since downgrade restores the global uniques.
